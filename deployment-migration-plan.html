Context

otjServices currently runs on a home-lab laptop via deploy/docker-compose.yml (mongo + mongo-express + the app/hours-api container). The app container needs NET_ADMIN/NET_RAW, /dev/net/tun, and elevated sysctls only because tailscaled runs inside it — docker/start.sh starts tailscaled, mints an ephemeral Tailscale auth key, joins the tailnet as its own node, and only then execs the Java app. The app identifies callers by having TailscaleIdentityHelper.java dial tailscaled's local Unix-socket API (whois on the raw TCP peer address) — this is what forces the container to be a full tailnet node with elevated privileges.

notes.md already flags “Upgrade to AWS, with free tier, not sure how that looks with running privileged containers though” as an open question — this plan resolves it.

Hosting

Cloud VM — AWS EC2 free tier or equivalent VPS

Runtime

Podman + systemd Quadlets, rootless

CI/CD deploy

Self-hosted GitHub Actions runner on the VM

Database

MongoDB Atlas free tier (M0)

The key unlock for “no elevated privileges”: move tailscaled out of the app container entirely and onto the host as a normal systemd service — that needs root at the OS level, same as any VPN daemon, and doesn't undermine the app container's lack of privileges. The host then runs tailscale serve to reverse-proxy tailnet traffic to the app container's loopback-only port, injecting an identity header (Tailscale-User-Login) into forwarded requests. TailscaleIdentityHelper.java reads that header instead of calling tailscaled's whois API directly — same method signature, nothing else in the app changes.

Also discovered along the way: the current Dockerfile installs Firefox + geckodriver, but neither OtjDriver.java nor SmartAssessorDriver.java use Selenium/WebDriver — "Firefox/151.0" only appears as a hardcoded User-Agent string. Dead weight, dropped from the new image. Same for start.sh's CSV bootstrap — zero references anywhere in src/.

01

MongoDB Atlas

Manual · console

Create a free-tier M0 cluster, a DB user scoped to otjdb, and get the SRV connection string.

mongodb+srv://<user>:<pass>@<cluster>.mongodb.net/otjdb?retryWrites=true&w=majority

No code change needed — AppModule.provideMongoClient() (bind/AppModule.java:40-44) already does MongoClients.create(System.getenv("MONGO_URI")); swapping the env var value is a pure config change. Verify Atlas SRV DNS resolution from inside the container during the step 4 smoke test — don't assume it silently works.

mongo and mongo-express disappear entirely — no Quadlet units for either.

02

Rewrite TailscaleIdentityHelper.java

Code change — done

src/main/java/com/github/grepHammerspace/tailscale/TailscaleIdentityHelper.java

Deleted the TAILSCALE_SOCKET constant, the static OkHttpClient with its custom SocketFactory/dummy Dns, the whois HTTP call, and the entire inner UnixSocket class — nothing else referenced any of it.

public class TailscaleIdentityHelper {
    private static final String IDENTITY_HEADER = "Tailscale-User-Login"; // verify against current docs

    public static String getUser(HttpServletRequest request) throws IOException {
        String user = request.getHeader(IDENTITY_HEADER);
        if (user == null || user.isBlank()) {
            throw new SecurityException(
                "Missing " + IDENTITY_HEADER + " header — request did not arrive via tailscale serve");
        }
        return user;
    }
}

Signature stays getUser(HttpServletRequest): String throws IOException — TailscaleIdentityService, its impl, AppModule.java, and OtjServicesResource.resolveUserState() needed zero changes. Tests are unaffected — TestAppModule already stubs the service with a fixed user.

Invariant

This header is only trustworthy because the app container is reachable exclusively on 127.0.0.1 — the only thing that can reach it is the host's tailscale serve process, which is what actually sets this header. If the bind address or network topology ever changes, re-examine this assumption.

03

New Dockerfile

Code change

Replace docker/otjService.Dockerfile:

FROM maven:3.9-eclipse-temurin-25 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline -q
COPY src/ ./src/
RUN mvn package -DskipTests -q

FROM eclipse-temurin:25-jre
RUN useradd --system --create-home --uid 10001 appuser
WORKDIR /app
COPY --from=build /app/target/app.jar app.jar
USER appuser
EXPOSE 8945
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

No Firefox/geckodriver, no curl jq gnupg/Mozilla apt repo, no tailscale binary stage. Runs as non-root appuser as defense-in-depth on top of rootless Podman. Delete docker/start.sh entirely — nothing left to wrap.

04

Local rootless-Podman smoke test

Manual · local

Before touching AWS at all:

podman build -t otj-hours-api:local -f docker/otjService.Dockerfile .
podman run -d --name otj-test -p 127.0.0.1:8945:8945 \
  -e MONGO_URI="mongodb+srv://...atlas.../otjdb?..." \
  -e ANTHROPIC_API_KEY="sk-ant-..." \
  otj-hours-api:local

curl -s http://127.0.0.1:8945/health                       # expect 200
curl -s -H "Tailscale-User-Login: test@example.com" \
  http://127.0.0.1:8945/otj-services/...                    # simulate the proxy header
podman inspect otj-test | grep -A5 CapAdd                  # expect empty

Confirms the Atlas connection, the header-based identity shim, and that rootless Podman needs zero cap_add/devices/sysctls once tailscaled is out of the container.

05

Provision the EC2 VM

Manual · console

Launch an Ubuntu/Debian LTS instance. Security group: SSH (22, restricted to your IP) only — no inbound rule for 8945, since all app traffic arrives via the tailnet, not the public internet. Allocate an Elastic IP (needed for the Atlas allowlist). Install Podman. Install Tailscale on the host and bring it up with a persistent, non-ephemeral auth:

curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --hostname=hours-api
Sizing

Free-tier t2.micro/t3.micro (1 GiB RAM) may be tight running a JVM + Podman + tailscaled concurrently — confirm budget for t3.small (2 GiB), or tune JVM heap flags if staying strictly free-tier.

06

Podman Quadlet unit

Manual · VM

Dedicated non-root user, lingering enabled so systemd --user survives logout/reboot:

sudo useradd -m -s /bin/bash otjapp
sudo loginctl enable-linger otjapp

As otjapp, ~/.config/containers/systemd/hours-api.container:

[Unit]
Description=otjServices hours-api
After=network-online.target
Wants=network-online.target

[Container]
Image=localhost/otj-hours-api:latest
ContainerName=hours-api
PublishPort=127.0.0.1:8945:8945
EnvironmentFile=%h/otj-hours-api.env
HealthCmd=curl -f http://localhost:8945/health || exit 1
HealthInterval=15s
HealthRetries=3

[Service]
Restart=always
RestartSec=5

[Install]
WantedBy=default.target

EnvironmentFile points at /home/otjapp/otj-hours-api.env (chmod 600, holding MONGO_URI=/ANTHROPIC_API_KEY=) — managed out-of-band on the VM, never in the repo, never touched by CI. No .network/.volume Quadlet files needed.

systemctl --user daemon-reload
systemctl --user enable --now hours-api.service

Confirm posture: podman inspect hours-api | jq '.[0].HostConfig.CapAdd, .[0].HostConfig.Privileged' → empty array / false.

07

Host-level tailscale serve

Manual · VM
sudo tailscale serve --bg --https=443 / http://127.0.0.1:8945

Exposes the service at https://hours-api.<tailnet>.ts.net/ to tailnet devices, with the host's tailscaled terminating TLS, forwarding to the loopback app, and injecting the identity header on the way in.

Verify, don't assume
  • Exact identity header name/casing Tailscale currently injects — confirm against current tailscale serve/Funnel docs.
  • MagicDNS + HTTPS Certificates enabled on the tailnet (required for --https to mint a cert).
  • Current Tailscale plan tier supports identity-header injection (historically free “Personal” tier does).
  • Whether the serve config persists across a host reboot, or needs a small startup script.
08

End-to-end verification

Manual

From a tailnet-joined device: curl https://hours-api.<tailnet>.ts.net/health and a real API call, then check app logs to confirm resolveUserState() resolves the actual tailnet identity rather than throwing SecurityException. Do this before wiring CI/CD.

09

Self-hosted GitHub Actions runner

Manual · one-time

As the otjapp user on the VM (simplest: same user that owns the Quadlet unit, avoiding cross-user systemctl --user permission issues): register via repo Settings → Actions → Runners → “New self-hosted runner”, label it otj-vm, install as a systemd service (svc.sh install && svc.sh start). This is inherently manual — GitHub's registration token is short-lived/single-use by design, so it can't be scripted into the workflow itself.

10

GitHub Actions workflow

Code change

.github/workflows/ci-cd.yml

name: CI/CD
on:
  push:
    branches: [master]
  pull_request:
    branches: [master]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '25', cache: maven }
      - run: mvn -B test

  deploy:
    needs: build-and-test
    if: github.ref == 'refs/heads/master' && github.event_name == 'push'
    runs-on: [self-hosted, otj-vm]
    steps:
      - uses: actions/checkout@v4
      - run: podman build -t localhost/otj-hours-api:latest -f docker/otjService.Dockerfile .
      - run: systemctl --user restart hours-api.service
      - run: |
          for i in $(seq 1 30); do
            curl -sf http://127.0.0.1:8945/health && exit 0
            sleep 2
          done
          echo "Service did not become healthy" >&2; exit 1

build-and-test runs on GitHub-hosted runners — mvn test doesn't need Testcontainers/Docker-in-Docker since pom.xml has no failsafe plugin wiring *IT.java into the test phase. deploy only fires on push to master after tests pass. No secrets flow through GitHub Actions — the container picks up env from the Quadlet's EnvironmentFile on the VM, managed out-of-band.

Likely rough edge

systemctl --user restart invoked from the runner's service context needs XDG_RUNTIME_DIR/DBUS_SESSION_BUS_ADDRESS set correctly. Running the runner as otjapp with lingering enabled should cover it — verify on the first real deploy.
