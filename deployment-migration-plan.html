Context

Where this started: otjServices ran on a home-lab laptop via deploy/docker-compose.yml (mongo + mongo-express + the app/hours-api container). The app container needed NET_ADMIN/NET_RAW, /dev/net/tun, and elevated sysctls only because tailscaled ran inside it — docker/start.sh started tailscaled, minted an ephemeral Tailscale auth key, joined the tailnet as its own node, and only then exec'd the Java app. The app identified callers by having TailscaleIdentityHelper.java dial tailscaled's local Unix-socket API (whois on the raw TCP peer address) — this is what forced the container to be a full tailnet node with elevated privileges.

What actually shipped (f497f31, “sudo-must-go”, PR #4): the container-privileges problem is solved, and so is the sudo problem — but by a smaller path than originally planned. The app still runs locally on the home-lab machine, not on an EC2 VM; orchestration is podman-compose (deploy/podman-compose.yaml, renamed from the old compose file), not systemd Quadlets; and Mongo/mongo-express still run as local containers, not Atlas. notes.md's “Upgrade to AWS” item is still explicitly un-checked — that part of this plan hasn't started.

The unlock that shipped: tailscaled runs on the host (already tailnet-joined), not inside the app container, and tailscale serve reverse-proxies tailnet traffic to the app container's loopback-only port, injecting an identity header (Tailscale-User-Login) into forwarded requests. TailscaleIdentityHelper.java reads that header instead of calling tailscaled's whois API directly — same method signature, nothing else in the app changed. Where it diverged from the original plan: instead of eliminating the remaining sudo requirement by standing up tailscaled as a fresh systemd unit on an EC2 VM, deploy/bootstrap.sh delegates Tailscale's local operator role to the current user with a single one-time sudo tailscale set --operator=$USER. After that one-time step, tailscale serve itself never needs sudo again, and bootstrap.sh wires it up automatically on every run.

Also discovered along the way: the old Dockerfile installed Firefox + geckodriver, but neither OtjDriver.java nor SmartAssessorDriver.java use Selenium/WebDriver — "Firefox/151.0" only appears as a hardcoded User-Agent string. Dead weight, dropped from the new image as planned. start.sh's CSV bootstrap logic was removed too, and its tailscaled-launching logic was stripped out — but the script itself was kept, not deleted as the original plan assumed, since it still needs to toggle the JAVA_DEBUG remote-debugging flag before exec'ing the jar.

02

Rewrite TailscaleIdentityHelper.java

Code change — done

src/main/java/com/github/grepHammerspace/tailscale/TailscaleIdentityHelper.java

Deleted the TAILSCALE_SOCKET constant, the static OkHttpClient with its custom SocketFactory/dummy Dns, the whois HTTP call, and the entire inner UnixSocket class — nothing else referenced any of it. This is the actual current file content, verified against src/main/java/com/github/grepHammerspace/tailscale/TailscaleIdentityHelper.java:

public class TailscaleIdentityHelper {
    private static final String IDENTITY_HEADER = "Tailscale-User-Login";

    /**
     * Reads the identity injected by the host's {@code tailscale serve} process. Trustworthy only
     * because the app is reachable exclusively via 127.0.0.1 — tailscale serve is the sole process
     * that can reach that loopback port and set this header.
     *
     * @throws IOException if the header is missing or blank, meaning the request did not arrive via tailscale serve
     */
    public static String getUser(HttpServletRequest request) throws IOException {
        String user = request.getHeader(IDENTITY_HEADER);
        if (user == null || user.isBlank()) {
            throw new IOException(
                    "Missing " + IDENTITY_HEADER + " header — request did not arrive via tailscale serve");
        }
        return user;
    }
}

Signature stays getUser(HttpServletRequest): String throws IOException — note it throws plain IOException, not SecurityException. TailscaleIdentityService, its impl, AppModule.java, and OtjServicesResource.resolveUserState() needed zero changes. Tests are unaffected — TestAppModule already stubs the service with a fixed user.

Invariant

This header is only trustworthy because the app container is reachable exclusively on 127.0.0.1 — the only thing that can reach it is the host's tailscale serve process, which is what actually sets this header. If the bind address or network topology ever changes, re-examine this assumption.

07

Host-level tailscale serve, no sudo

Code + manual · done (locally)

Shipped in f497f31 (“sudo-must-go”) — differs from the original plan of running tailscale serve under sudo from a fresh systemd unit. Instead, a one-time manual delegation of Tailscale's local operator role:

sudo tailscale set --operator=$USER   # once, ever

After that, deploy/bootstrap.sh checks for it and wires up tailscale serve automatically, with no sudo, on every run:

# True if `tailscale serve` can run as $USER without sudo (operator delegated once via
# `tailscale set --operator=$USER`).
tailscale_operator_set() {
  command -v tailscale &>/dev/null || return 1
  local operator
  operator=$(tailscale debug prefs 2>/dev/null | jq -r '.OperatorUser // empty')
  [ -n "$operator" ] && [ "$operator" = "$USER" ]
}

if tailscale_operator_set; then
  tailscale serve --bg --https=443 "http://127.0.0.1:$APP_PORT"
else
  echo "NOTE: run 'sudo tailscale set --operator=$USER' once, then re-run this script."
fi

Exposes the service at https://<hostname>.<tailnet>.ts.net/ to tailnet devices, with the host's tailscaled terminating TLS, forwarding to the loopback app, and injecting the identity header on the way in. See deploy/README.md for the write-up of this trust model. The EC2-hosted version of this step (steps 05–06) will reuse the same operator-delegation mechanism — it isn't tied to the laptop.

Verify, don't assume
  • Exact identity header name/casing Tailscale currently injects — confirm against current tailscale serve/Funnel docs.
  • MagicDNS + HTTPS Certificates enabled on the tailnet (required for --https to mint a cert).
  • Current Tailscale plan tier supports identity-header injection (historically free “Personal” tier does).
  • Whether the serve config persists across a host reboot, or needs a small startup script.

GitHub Actions workflow

Code change — not started

No .github/workflows/ directory exists yet. Proposed .github/workflows/ci-cd.yml:

name: CI/CD
on:
  push:
    branches: [master]
  pull_request:
    branches: [master]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '25', cache: maven }
      - run: mvn -B test

  deploy:
    needs: build-and-test
    if: github.ref == 'refs/heads/master' && github.event_name == 'push'
    runs-on: [self-hosted, otj-vm]
    steps:
      - uses: actions/checkout@v4
      - run: podman build -t localhost/otj-hours-api:latest -f docker/otjService.Dockerfile .
      - run: systemctl --user restart hours-api.service
      - run: |
          for i in $(seq 1 30); do
            curl -sf http://127.0.0.1:8945/health && exit 0
            sleep 2
          done
          echo "Service did not become healthy" >&2; exit 1

build-and-test runs on GitHub-hosted runners — mvn test doesn't need Testcontainers/Docker-in-Docker since pom.xml has no failsafe plugin wiring *IT.java into the test phase. deploy only fires on push to master after tests pass. No secrets flow through GitHub Actions — the container picks up env from the Quadlet's EnvironmentFile on the VM, managed out-of-band.

Likely rough edge

systemctl --user restart invoked from the runner's service context needs XDG_RUNTIME_DIR/DBUS_SESSION_BUS_ADDRESS set correctly. Running the runner as otjapp with lingering enabled should cover it — verify on the first real deploy.
