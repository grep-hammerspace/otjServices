Auth & multi-user plan · otjServices

The tailnet was the password.

Today the app has no authentication code at all — tailscale serve injects a header and the app trusts it. To put this in front of ~100–120 users on a public HTTPS endpoint, identity has to become something the app actually owns: an invite-gated account, a bcrypt password, and a sliding 30-day bearer token.

Context

Where this starts: there is no application-level auth in the codebase. TailscaleIdentityHelper reads a Tailscale-User-Login header, and that header is trustworthy only because the app binds to loopback and tailscale serve is the sole process that can reach it. Identity, transport encryption, and reachability are all the same mechanism. Every endpoint calls resolveUserState(request), which is a header read plus a lazy state init.

Why that has to change: a mobile app distributed to ~100–120 people can't require each of them to join a private tailnet. Moving to public HTTPS breaks the trust invariant completely — TLS gives anyone a secure pipe to the server, so the network stops authenticating callers and a per-user secret becomes mandatory. A username alone is an identifier, not a credential; without a token, anyone knowing asad_yezdan could call /delete-last-row as them.

The compensating win: because OneAdvanced credentials are replayed into a browser login rather than verified, they currently have to be stored recoverably — hence PasswordCipher's AES-256-GCM and the PASSWORD_ENCRYPTION_KEY it depends on. Moving those credentials onto the device (iOS Keychain / Android Keystore) and sending them per-call over TLS deletes that whole subsystem. After this plan the server stores no credential that logs in anywhere — only bcrypt hashes and SHA-256 token hashes. A full database compromise leaks nothing usable.

Identity

Username + bcrypt password → sliding 30-day bearer token

OneAdvanced creds

Never stored. Device Keychain, sent per-call over TLS

Account creation

Invite-code only — codes minted by hand in the Atlas UI

Ingress

Caddy native on the EC2 box, Let's Encrypt on the EIP · tailscale serve demoted to a dev tunnel

Build order rationale: the KSB deletion goes first because it removes a resource, a service, five classes and two prompt files that every later step would otherwise have to be threaded through. Infra goes last because nothing in it is required to develop or test the auth work — the app runs fine on loopback throughout. Everything between is sequenced so the app compiles and the suite passes at each step.

02

Session token core

Code change

New package com.github.grepHammerspace.auth.

SessionTokenService — @Singleton, @Inject constructor taking the existing MongoDatabase, so no explicit Dagger provider is needed. Issues a 32-byte SecureRandom token, base64url-encoded, and stores only its SHA-256 hash in a new sessions collection. The raw token is returned once and never persisted — same model as a GitHub PAT.

{ tokenHash: "<sha256 hex>", userId: "<uuid>", expiresAt: ISODate, createdAt: ISODate }

Sliding expiry. resolve(rawToken) looks up by hash, rejects if expiresAt has passed, and otherwise pushes expiresAt back out to now + 30 days. To avoid a Mongo write on every single request, only extend when less than half the window remains. An active user therefore never sees a login screen again; a token unused for 30 days dies on its own.

AuthenticationFilter — a JAX-RS ContainerRequestFilter. Reads Authorization: Bearer <token>, resolves it to a userId, and sets a SecurityContext whose principal name is that userId. Missing, malformed, unknown or expired token → 401, request never reaches the resource.

@Authenticated — a @NameBinding annotation applied to OtjServicesResource. Cleaner than path matching in the filter: AuthResource and HealthResource simply don't carry the annotation, so they stay anonymous by construction rather than by an exemption list that can drift.

Rewire the resource. OtjServicesResource loses its TailscaleIdentityService field and constructor argument; every method swaps @Context HttpServletRequest for @Context SecurityContext. resolveUserState collapses to a userStateStore.createUserState(...) call and stops throwing IOException — which deletes six try/catch blocks and their duplicated 401 branches, since the filter owns that now.

@POST @Path("/log-activities")
public Response logActivities(@Valid ActivityLogRequest body, @Context SecurityContext sc) {
    String userId = sc.getUserPrincipal().getName();
    userStateStore.createUserState(userId);
    ...

Delete the tailscale package entirely — TailscaleIdentityService, TailscaleIdentityServiceImpl, TailscaleIdentityHelper — and remove provideTailscaleIdentityService from AppModule. Register the filter on the ResourceConfig in ServerBootstrap.

03

User model & bcrypt

Code change

Add the hashing dependency to pom.xml — at.favre.lib:bcrypt, chosen because it is small and pulls no transitive dependencies. Hand-rolling PBKDF2 on the JDK would avoid the dependency but is easier to get subtly wrong.

The User record changes meaning, not just shape. Today username/password are the OneAdvanced credentials. Afterwards they are this app's own login. Rename deliberately so the two can never be confused during the refactor:

// before
record User(String userId, String username, String password, String learnerId)

// after
record User(String userId, String appUsername, String appPasswordHash,
            String learnerId, Instant createdAt)

userId becomes a generated UUID rather than a tailnet login name. Nothing downstream cares — ActivityLog, UserStateStore and the driver methods all treat it as an opaque string.

learnerId stays server-side, captured once at signup. It is not a secret, it is embedded in every ActivityLog row, and keeping it on the user record avoids threading it through every request body for no security benefit.

UserRepository — drop the PasswordCipher injection and both encrypt/decrypt calls; add findByAppUsername() for login and an insert that fails closed on a duplicate username. lastContent handling is unchanged: it is diff state, not a secret, and stays where it is.

Delete crypto/PasswordCipher.java, crypto/PasswordCipherTest.java, testutil/TestKeys.java, the providePasswordCipher bindings in both AppModule and TestAppModule, and every reference to PASSWORD_ENCRYPTION_KEY in compose files, .env, CI and the SSM deploy script.

04

Invite-gated signup

Code change + Atlas UI

Open signup would let anyone create an account and start spending Anthropic credits via /log-activities, even though they could never post a real OTJ without genuine OneAdvanced credentials. The gate has to be server-side: limiting who can install the app is not a control, because the API is a public HTTPS endpoint that anyone can reach with curl.

New inviteCodes collection, with a schema deliberately simple enough to hand-write — the Atlas UI is the admin console, so there is no admin endpoint to build, authenticate or protect:

{ code: "OTJ-7F3K-9QMX", used: false, note: "for Sam",
  createdAt: ISODate, expiresAt: ISODate, usedBy: null, usedAt: null }

To mint a code, insert a document. To revoke, set used: true or delete it.

AuthResource — new, un-annotated (anonymous) resource:

POST   /auth/signup    { inviteCode, username, password, learnerId } -> { token }
POST   /auth/session   { username, password }                       -> { token }
DELETE /auth/session   (Bearer)                                     -> 204

Signup claims the code atomically — findOneAndUpdate on {code, used:false, expiresAt:{$gt:now}} setting used:true. Atomicity is what stops two people racing the same code. Then it rejects duplicate usernames, bcrypts the password, creates the UUID userId, and returns a session token so signup and login are one round trip.

DELETE /auth/session deletes the token row, giving instant revocation independent of the 30-day window.

05

Stop storing OneAdvanced credentials

Code change

The credentials move to the device — iOS Keychain via react-native-keychain, or Android Keystore-backed storage — and are sent on each call that needs a OneAdvanced login. The server holds them in memory only for the duration of that call: AzureIdDriver.prepare() posts the password as a form field to Microsoft and retains only the username as mfaLogin between prepare and completeMfa. There is no browser and no Selenium anywhere in this — the drivers are OkHttp plus Jsoup, replaying the login flow as plain HTTP. That transient exposure exists in the current design too; what disappears is the at-rest copy.

Delete POST /otj-services/register and dto/RegisterRequest.java. Registration as a concept is replaced by signup (app account) plus on-device storage (OneAdvanced vault).

Breaking endpoint changes — both become POST because they now carry a body:

WasBecomesBody
GET /prepare-browserPOST /prepare-browser{oneAdvancedUsername, oneAdvancedPassword}
GET /azure-id/preparePOST /azure-id/prepare{oneAdvancedUsername, oneAdvancedPassword}

Both feed straight into the existing driver.prepare(username, password) signatures — those already take credentials as parameters, so the drivers themselves need no change. New DTOs PrepareBrowserRequest and AzureIdPrepareRequest, both fields @NotBlank. /azure-id/complete, /submit-with-mfa, /delete-last-row and /reset-notes are unchanged — none of them need credentials.

Must fix
OtjServicesResource.java:237 currently logs the MFA code in plaintext: log.info("...and mfa code {}", body.mfaCode()). Delete that line. Once passwords arrive in request bodies, the same habit would write credentials into logs and any aggregator downstream — audit every log.* and error-response string in the resource for sensitive fields.
06

Rate limiting

Code change

auth/RateLimiter.java — in-memory sliding window over a ConcurrentHashMap with periodic eviction. In-memory is correct here rather than a shortcut, because there is exactly one app instance; note that it resets on restart. Applied only in AuthResource:

  • POST /auth/session — per-IP and per-username. The per-username limit is the one that matters: usernames are public identifiers, so they are the brute-force surface.
  • POST /auth/signup — per-IP, tighter, to stop invite-code guessing.

Respond 429 with Retry-After. Behind Caddy the client IP arrives in X-Forwarded-For, and the app must read that rather than getRemoteAddr(), which sees only the proxy and would rate-limit every user as one.

Must fix
reverse_proxy appends to X-Forwarded-For by default. If a client sends its own header, Caddy appends after it and the first hop becomes attacker-controlled — per-IP limiting is then trivially evaded by sending a fresh fake IP each request. Step 09's Caddyfile therefore uses header_up X-Forwarded-For {remote_host}, which replaces the header outright. Only with that directive in place is “read the first hop” the correct rule.
07

Per-user LLM quota

Code change

Every /log-activities call spends Anthropic credits. After step 01 this is the only LLM call site, so the quota is a single number: 10 calls per user per day.

quota/LlmQuotaService.java — atomic $inc against a {userId, date} document with a unique index. Checked in logActivtiesWithLlmHelp after the ContentDiffer no-op check but before llmService.parseActivities, so identical resubmitted content never consumes quota. Exhausted → 429.

Backstop
An application-level quota cannot protect against a bug in the server's own retry logic. Set a spend limit in the Anthropic console as well — that is the only cap that holds unconditionally.

09

Ingress & infra

Manual + CDK

The Elastic IP in aws/lib/otj-services-stack.ts is already a public, internet-routable address on a public subnet with an internet gateway — routing works today. The only reason nothing can connect is the security group, which is deliberately configured with zero inbound rules. It was provisioned for a different purpose (a stable egress IP for the Atlas allowlist); the same address will now serve traffic.

Decision: the box stays. Dropping Tailscale does not imply dropping EC2 — Caddy replaces tailscale serve in place and everything else in deploy/ stands. ECS Fargate was considered and rejected on three counts:

  • The Atlas allowlist depends on a stable egress IP. Fargate tasks draw an ephemeral public IP that changes on every task replacement, so the allowlist would break on each deploy. The fixes all cost more than the box does: a NAT gateway with an EIP (~$32/mo plus data processing), an Atlas private endpoint (M10+, ~$57/mo), or opening Atlas to 0.0.0.0/0 — which discards a control that already works.
  • Session state is in-process. UserStateStore is a ConcurrentHashMap holding a live Driver and its InMemoryCookieJar per user, so prepare → submit-with-mfa must land on the same process. More than one task would need sticky routing — and ALB cookie stickiness does not help a mobile client sending Bearer headers. Fargate therefore buys no horizontal scaling until the cookie jar moves into Mongo.
  • Cost. The t3.small is ~$15/mo. An equivalent always-on task plus ALB plus NAT lands near ~$66/mo, for no capability this workload needs at 100–120 users.

Worth recording for whoever revisits this: if the service ever does move to Fargate, Caddy is deleted rather than migrated. An ALB terminates TLS with a free auto-renewing ACM certificate and sets X-Forwarded-For natively, which is Caddy's entire job here. Running it as a sidecar would mean re-solving certificate persistence on ephemeral storage — re-issuing on every task start, straight into Let's Encrypt rate limits. It is Caddy-on-EC2 or ALB-on-Fargate, never both.

  • CDK: add inbound 443 and 80 to InstanceSecurityGroup. Port 80 is needed for the Let's Encrypt HTTP-01 challenge, not for serving. Update the now-inaccurate comment block above it, which describes the no-inbound/tailscale-serve model.
  • Domain: register one and point an A record at the EIP. A public CA won't issue against a bare IP in the normal case, so a hostname is required. The pre-existing EIP means the record won't break across instance restarts.
  • Caddy natively via apt, not as a Quadlet unit. The deploy is rootless throughout — systemctl --user, %h/otj-hours-api.env — and rootless podman cannot bind ports below 1024, so a rootless Caddy container fails to bind 443 outright. The workarounds (an ip_unprivileged_port_start sysctl, or a root-owned Quadlet) both add moving parts, and a containerised Caddy would additionally need host networking to reach the app on 127.0.0.1:8945. The Debian package ships its own systemd unit and certificate storage under /var/lib/caddy, and reaches loopback with no networking gymnastics. The app stays bound to loopback either way — Caddy simply replaces tailscale serve as the thing in front of it.
  • /etc/caddy/Caddyfile is the whole configuration: 
    otj.<yourdomain> {
    reverse_proxy 127.0.0.1:8945 {
        header_up X-Forwarded-For {remote_host}
    }
}
    The header_up line is not optional — see the callout in step 06.
  • Provisioned once, by hand, over SSM. deploy/prod/deploy.sh renders only hours-api.container and needs no change: Caddy is host setup, not part of the per-commit deploy path, and app deploys restart the container behind it without touching it. Add it to deployment-checklist.md as a one-time step alongside the Atlas setup.
  • SSM remains the admin path. No SSH, no inbound 22.
  • Rewrite deploy/README.md: the “Identity: header instead of in-container Tailscale” section becomes “Dev tunnel”, and the trust-invariant paragraph is deleted — it stops being true and stops being load-bearing.
Check
Certificate state lives in /var/lib/caddy and must survive restarts, or every boot re-issues. Let's Encrypt allows only five duplicate certificates per week, so validate against the staging CA first — add acme_ca https://acme-staging-v02.api.letsencrypt.org/directory to the site block, confirm the chain end to end, then remove the line for the real issuance. Staging certificates are untrusted by design; the phone will refuse them, which is the expected result at that stage.

What the mobile client needs: nothing. TLS here is server-authenticated only, so no client certificate, no bundled trust store, no device configuration. Every iOS and Android device already trusts the Let's Encrypt roots, so the app is a plain https:// call. Caddy's defaults satisfy iOS App Transport Security (TLS 1.2+, forward secrecy, SHA-256) with no Info.plist exception, and Android's cleartext block is moot on HTTPS. Certificate pinning is deliberately not used — it defends only against a compromised or user-installed CA, and risks an app-breaking outage every renewal cycle.

deploy/ and its podman-compose stack stay exactly as they are, for local development. tailscale serve remains useful there — it gives a real certificate on a .ts.net name, so a phone can exercise the true production HTTPS path against a laptop with no domain and no self-signed-certificate warnings. It is a dumb tunnel now: the injected identity header is ignored, and local dev authenticates with a password like everything else.

Verification

  • A request to any /otj-services/* endpoint with no Authorization header returns 401, and with a valid token succeeds.
  • A token belonging to user A cannot read or mutate user B's activity logs.
  • Signup without a valid invite code returns 403; the same code cannot be redeemed twice, including concurrently.
  • grep -ri "PASSWORD_ENCRYPTION_KEY\|PasswordCipher\|Tailscale" src/ returns nothing.
  • The users collection contains no field from which any password can be recovered.
  • Server logs across a full login → prepare → MFA → submit cycle contain no password and no MFA code.
  • The 11th /log-activities call in a day returns 429; the counter rolls over the next day.
  • Repeated bad-password attempts against a known username trip the limiter.
  • Mongo indexes exist: users.appUsername unique, sessions.tokenHash unique, sessions.expiresAt TTL, inviteCodes.code unique.
  • End to end from a phone over public HTTPS with a valid certificate, no tailnet involved.

No data migration is required — the application has no users other than its author. Drop the users collection and sign up again. Existing ActivityLog rows keyed by the old tailnet login will be orphaned from the new UUID accounts; that is acceptable and they can be dropped too.

Still open

Domain name — not yet registered. Step 09 is blocked on it, though every other step is not.

The mobile client is out of scope here. What this plan fixes for it: one code path for every deployment — POST /auth/session, store the token in Keychain or Keystore, send Authorization: Bearer on everything else, and hold the OneAdvanced credentials in the same secure storage, ideally behind a biometric prompt. That biometric gate, not a short token lifetime, is what actually protects a stolen phone.

Token sharing — DPoP versus accepting it. A bearer token is copyable by definition: nothing in step 02 distinguishes the device the token was issued to from a device it was pasted into. Two users can share one account and the server cannot tell. There are exactly two honest positions.

Bind the token to hardware (DPoP). The client generates a P-256 keypair in the Secure Enclave or StrongBox — non-exportable, so it cannot leave the device even on a jailbreak — and registers the public key at signup, where its JWK thumbprint is stored on the session row. Every request then carries a short JWT signed over method, URI, timestamp and token hash, which the filter verifies against that thumbprint. The token stops being a credential on its own and becomes a pointer to a key, so copying it achieves nothing. Server side this is perhaps 150 lines against java.security.Signature; the real cost is client work, a nonce or timestamp window to stop replay, and a recovery path for when a user's key is lost with their phone. Mutual TLS gets the same property but requires operating a private CA, an enrolment flow and revocation for 120 people — strictly more machinery for the same guarantee.

Accept it, and cap the damage instead. The reason this is defensible here rather than lazy: a shared account still cannot post an OTJ, because after step 05 the OneAdvanced credentials live only on the legitimate user's device and never touch the server at rest. The step 07 quota is per userId, so two people sharing one account split ten LLM calls a day rather than getting twenty — the economic damage is bounded by construction. Sharing degrades the sharer's own experience and costs the operator nothing extra.

Recommendation: accept it for now, and add the two cheap detectors rather than the expensive fix. Record lastSeenIp and user-agent on the session row — free, because step 02 already writes to that row when the sliding window passes its halfway point — and treat one session used from two networks minutes apart as a signal to revoke and force re-login. If sharing ever becomes a real problem, single-active-session (a deleteMany({userId}) before each insert) makes it self-punishing at the cost of multi-device use, and DPoP remains available as the actual fix. Building DPoP first would be solving a problem this deployment has not yet demonstrated it has.

Residual risk, stated plainly. This design defeats network attackers and anyone who merely knows a username. It does not defeat someone who learns a user's password, or a rooted device where an attacker can read the Keychain. Expiry, revocation and biometrics are the mitigations; there is no version of bearer-token auth without that residue. The meaningful improvement is that the blast radius of a compromise moves from the server — where it would have been every user's institutional credentials — to a single device.
